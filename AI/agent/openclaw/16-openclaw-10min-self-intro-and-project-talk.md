# OpenClaw 10 分钟自我介绍与项目表达稿

## 适用场景

- 面试官说：“介绍一下你最近研究最深的项目/系统。”
- 面试官说：“挑一个你比较熟悉的开源项目，讲讲你的理解。”
- 面试官说：“你最近在 AI Agent 方向做了什么学习或实践？”
- 面试官说：“你来做一个 5 到 10 分钟的项目介绍。”

## 使用建议

- 这份稿子不是要求你逐字背诵，而是给你一个稳定的表达结构。
- 最推荐的说法是：**先讲背景，再讲架构，再讲关键模块，再讲你的理解和收获。**
- 如果时间不够，可以只讲“3 分钟版”。
- 如果面试官愿意深入问，再切到“10 分钟完整版”。

## 一、30 秒开场版

如果面试官刚开始问，你可以先用这段把场子打开：

> 我最近重点研究了一个开源项目，叫 OpenClaw。它不是传统意义上的聊天机器人，而是一个运行在用户自己设备上的个人 AI 助手平台。  
> 它的核心能力是把多种消息渠道、Agent 运行时、长期会话、工具系统、记忆系统和插件体系统一起来。  
> 我之所以重点研究它，是因为它比普通的 Agent Demo 更接近真实落地系统，里面既有 LLM 和工具调用，也有控制平面、权限边界、状态管理和工程化问题，所以我觉得非常适合作为系统设计和 AI Agent 工程化的学习样本。

这段的目标不是讲全，而是把“项目级别”和“你为什么研究它”先立住。

## 二、3 分钟版项目介绍

### 1. 先讲项目定位

> 如果让我用一句话定义 OpenClaw，我会说它是一个本地优先的个人 AI 助手平台。  
> 它和普通 bot 最大的区别，是它不是只挂在某个聊天窗口里回答问题，而是把 WhatsApp、Telegram、Slack、Discord 这些消息渠道，以及 CLI、Web UI、macOS、iOS、Android 这些客户端和设备能力统一起来，让同一个助手跨多个入口工作。

### 2. 再讲整体架构

> 它的架构我一般分三层理解。  
> 第一层是 Gateway，也就是控制平面。它负责消息接入、WebSocket/HTTP 协议、会话管理、路由、插件加载、健康检查和安全控制。  
> 第二层是 Agent Runtime，也就是执行平面。它负责真正的上下文组装、模型调用、工具循环、流式输出和子 Agent 生命周期。  
> 第三层是扩展平面，比如插件系统、Context Engine、Memory、Browser、Canvas、Node 能力等。这样系统既能跑得起来，也能长期扩展。

### 3. 再讲一条真实消息链路

> 一条消息进入系统之后，首先由渠道插件标准化成统一消息结构；然后 Gateway 做去重、防抖、DM 配对和路由匹配；接着根据 `dmScope` 算出 sessionKey，把消息放进对应会话队列；再往下进入 Agent Runtime，组装系统提示、历史消息和工具定义，调用模型；如果模型触发工具，就执行工具并回填结果，直到生成最终文本；最后再通过对应渠道插件把消息发回去。  
> 所以它不是“消息一来就直连模型”，而是中间有一套比较完整的控制和编排层。

### 4. 最后讲你的评价

> 我觉得这个项目最值得学习的地方有三个。  
> 第一，它把 AI Agent 做成了一个长期运行系统，而不是一次性脚本。  
> 第二，它对 session、routing、tools、memory 这些容易被 Demo 忽略的东西做了完整建模。  
> 第三，它的插件边界和上下文边界设计得比较清楚，说明作者是在按平台化思路做，而不是按功能堆砌思路做。

## 三、10 分钟完整版表达稿

下面这版更适合技术面、二面、架构面，或者面试官明确说“你详细展开讲讲”。

### 第一部分：我为什么选择讲 OpenClaw

> 我之所以会重点研究 OpenClaw，而不是只看一些 Agent Demo，是因为我发现很多 Agent 项目都很擅长展示“模型会调工具”，但真正落地时最难的部分，往往不是 prompt 本身，而是系统怎么长期稳定运行。  
> 比如说，消息从哪里进来、多个用户怎么隔离、多个会话怎么管理、工具权限怎么控制、模型失败怎么恢复、上下文过长怎么办、怎么让扩展能力可维护，这些问题如果没有工程化方案，Agent 很难真正变成可用系统。  
> OpenClaw 正好覆盖了这些问题，所以我把它当成一个学习 AI Agent 工程化的典型案例。

### 第二部分：项目定位和核心特征

> 我会把 OpenClaw 定义成一个本地优先的个人 AI 助手平台。  
> 它有几个非常鲜明的特点。  
> 第一是 Local-first，也就是 Gateway 默认跑在用户自己的机器上，很多状态也保存在本地。  
> 第二是多入口统一，一个助手可以接多种消息渠道，也可以接 CLI、Web、移动端和桌面端。  
> 第三是多 Agent 隔离，不同 Agent 拥有自己的 workspace、session、memory、tools 和 auth profiles。  
> 第四是插件化，一大批能力不是写死在核心里的，而是通过插件注册，比如通道、模型、记忆系统、上下文引擎、搜索工具等。

### 第三部分：整体架构怎么理解

> 架构上我把它分成三层。  
> 第一层是 Gateway 控制平面。它统一接所有通道，统一维护 session、presence、health、route、plugin runtime 和安全策略。  
> 第二层是 Agent Runtime。它负责真正执行用户请求，包括上下文组装、模型调用、工具循环、流式输出和子 Agent 执行。  
> 第三层是扩展层，也就是 Plugins、Context Engine、Memory、Browser、Canvas、Node 能力等。  
> 这样拆的好处是，控制逻辑、执行逻辑和扩展逻辑不会混在一起，系统层次更稳定。

### 第四部分：我觉得最重要的模块是 Gateway

> 如果让我选一个最核心的模块，我会选 Gateway。  
> 因为它本质上是整个系统的控制平面。消息先从各个渠道进入 Gateway，Gateway 再做去重、防抖、DM pairing、allowlist 检查、bindings 路由、sessionKey 解析和队列管理。  
> 我觉得它最有价值的一点，是它把多入口系统的共享状态都收束到了一个中心。这样 session、routing、token usage、health、channel runtime 都有统一数据源，不需要每个客户端自己维护一份。  
> 当然它也有代价，就是会形成一个比较大的核心模块，但这在复杂系统里其实是合理的工程权衡。

### 第五部分：Agent Runtime 为什么值得重点讲

> Agent Runtime 的亮点在于，它不是简单调一次模型，而是一个完整的 Agent Loop。  
> 一次 run 开始后，系统会先准备 workspace、skills、bootstrap 文件、系统提示和 session 历史；然后调用模型；如果模型返回的是工具调用，就执行工具并把工具结果写回上下文；之后再继续调用模型，直到产出最终可渲染回复。  
> 这个过程中还会处理 NO_REPLY、消息工具去重、工具报错回退、流式输出、compaction 和重试。  
> 所以它不是一个“函数”，而是一个带状态、带多阶段事件、带容错机制的执行引擎。

### 第六部分：我觉得最能体现工程能力的是 Session 和 Queue

> 很多 Demo 项目都会讲模型和工具，但我觉得 OpenClaw 更有价值的是它对 Session 的建模。  
> 它的 session 不只是聊天历史，而是消息边界、上下文边界、执行串行化边界和存储边界的统一抽象。  
> 比如 `dmScope` 决定一个私聊到底是共享主会话，还是按人、按通道、按账号隔离。  
> 这件事表面上像配置项，实际上直接决定了会不会发生多用户上下文串话，所以本质上是安全设计。  
> 再加上 per-session 队列和全局并发控制，就能保证同一会话内的一致性，同时控制系统整体吞吐。

### 第七部分：插件体系为什么成熟

> OpenClaw 的插件体系我也很认可。  
> 因为它不是简单把代码拆成多个目录，而是有完整的 manifest、registry、loader、hook、slot 和 Plugin SDK 体系。  
> 尤其是它对导入边界要求非常严格，插件只能通过 `openclaw/plugin-sdk/*` 这种公共表面接入，不能直接依赖核心 `src/**`。  
> 这样做虽然前期看起来麻烦，但长期看可以显著降低耦合，让核心能继续演进。  
> 另外，像 memory 和 context engine 这种能力还做成了 slot，也就是同一时刻只能有一个主实现，这也很符合平台化设计。

### 第八部分：Context Engine 和 Memory 为什么有意思

> 我觉得 OpenClaw 另一个很值得学的点，是它没有把上下文管理硬编码死，而是抽象成了 Context Engine。  
> 这样上下文的摄入、组装、压缩和回合后维护都可以替换。  
> 在记忆这块，它又采取了“文件是主数据、索引和向量库是加速层”的思路。  
> 也就是说，用户真正长期记住的信息是 `MEMORY.md` 和 `memory/*.md` 这些文件，向量检索只是帮助召回。  
> 我觉得这种方案比纯黑盒数据库更适合个人 AI assistant，因为它更透明、可编辑、可调试。

### 第九部分：安全为什么做得比较完整

> OpenClaw 的安全模型我觉得也值得提。  
> 它不是简单加个 token，而是分成多层：传输安全、认证模式、设备身份、配对审批、DM 策略、速率限制、Origin 检查、RBAC、工具权限和可选沙箱。  
> 特别是它把多用户 DM 场景下的 session 隔离也当成安全问题来建模，我觉得这一点很成熟。  
> 因为很多系统只想到“谁能进来”，没想到“进来以后是不是还在同一个上下文里”。

### 第十部分：我从这个项目里学到了什么

> 我从这个项目里最大的收获有三点。  
> 第一，AI Agent 真正难的是系统工程，而不是只会写 prompt。  
> 第二，session、route、tool、memory 这些能力必须一起设计，不能只看单点功能。  
> 第三，做平台型系统时，边界设计比功能数量更重要。  
> 所以如果以后我要自己做一个类似系统，我会优先把 Gateway、Session、Runtime 和权限模型搭稳，再慢慢把能力插件化，而不是一开始就疯狂加工具。

### 第十一部分：一句话总结收尾

> 如果让我最后用一句话总结 OpenClaw，我会说：它最值得学习的地方，不是它支持了多少模型和渠道，而是它把 AI Agent 做成了一个有控制平面、有状态边界、有安全模型、有插件体系的长期运行系统。

## 四、可直接背诵的 1 分钟 / 3 分钟 / 10 分钟模板

### 1 分钟模板

> 我最近重点研究了一个开源项目叫 OpenClaw。它不是普通聊天机器人，而是一个本地优先的个人 AI 助手平台。  
> 它的特点是把多种消息渠道、Agent Runtime、会话系统、工具系统、记忆系统和插件体系统一起来。

> 所以我把它当作 AI Agent 工程化落地的一个典型样本来研究。

### 3 分钟模板

> 我最近研究比较深的一个项目是 OpenClaw。  
> 它是一个运行在用户自己设备上的个人 AI 助手平台，不只是单一聊天 bot。它可以接 WhatsApp、Telegram、Slack、Discord 这些消息渠道，也可以接 CLI、Web、桌面端和移动端。  
> 它的架构我一般分成三层。第一层是 Gateway，也就是控制平面，负责消息接入、路由、session、插件加载和安全控制；第二层是 Agent Runtime，负责上下文组装、模型调用、工具循环和流式输出；第三层是插件和能力层，比如 Context Engine、Memory、Browser、Canvas 和各类 Provider。  
> 我觉得它最有价值的地方在于，它真正考虑了 Agent 长期运行会遇到的问题，比如多用户私聊怎么隔离、会话过长怎么压缩、模型失败怎么恢复、工具权限怎么控制，而不是只展示“模型会调工具”。  
> 所以我研究它的重点，不是背 API，而是学习它怎么把 AI Agent 做成一个真正可运行的系统。
