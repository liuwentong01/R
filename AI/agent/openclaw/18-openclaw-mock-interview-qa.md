# OpenClaw 模拟面试问答（真实对话风格）

## 使用说明

- 这份材料不是知识点罗列，而是按真实面试对话方式来写。
- 你可以把它当成“演练稿”，直接练开口表达。
- 建议练习方式：
  - 第一遍：只看问题，自己回答。
  - 第二遍：对照参考答案，补结构和细节。
  - 第三遍：尝试脱稿，把答案压缩到 1 分钟、展开到 3 分钟都能说。

## 第一组：项目介绍型

### 模拟 01

**面试官：** 你最近研究比较深的一个项目是什么？  
**你：** 我最近研究比较深的是一个开源项目，叫 OpenClaw。它不是普通聊天机器人，而是一个本地优先的个人 AI 助手平台。它的核心价值不是单纯“回答问题”，而是把多种消息渠道、多个客户端入口、Agent 运行时、工具系统、记忆系统和插件体系统一起来，形成一个长期在线的助手系统。

我之所以重点研究它，是因为它比很多 Agent Demo 更接近真实落地场景。很多项目会重点展示“模型会调工具”，但 OpenClaw 还认真处理了消息从哪里进来、多个用户怎么隔离、上下文怎么长期维护、模型失败怎么恢复、权限怎么控制、系统怎么扩展这些更工程化的问题。所以我把它当成一个 AI Agent 工程化落地的典型样本来研究。

如果从架构上说，我一般会把它分成三层。第一层是 Gateway，也就是控制平面，负责消息接入、路由、会话管理、插件加载和安全控制。第二层是 Agent Runtime，负责真正的上下文组装、模型调用、工具循环、流式输出和子 Agent 生命周期。第三层是扩展层，比如 Memory、Context Engine、Browser、Canvas、Node 能力和各种 Provider 插件。这样它就不是一个单纯聊天框，而是一个有状态、有边界、有扩展能力的长期运行系统。

### 模拟 02

**面试官：** 那你觉得 OpenClaw 和普通聊天机器人最大的区别是什么？  
**你：** 我觉得最大的区别有四个。第一，它是 Local-first 的，强调运行在用户自己控制的设备或机器上，而不是完全云端托管。第二，它是多入口统一的，不只是在一个网页里聊天，而是可以接 WhatsApp、Telegram、Slack、Discord，也能接 CLI、Web UI、电脑和手机端。第三，它支持多 Agent，每个 Agent 有自己的 workspace、session、memory、tools 和 auth profile，所以不是所有事情都塞在一个助手里。第四，它高度插件化，通道、模型、记忆、上下文引擎和工具都可以替换和扩展。

如果换一个更通俗的说法，普通聊天机器人更像“一个会回复消息的账号”，而 OpenClaw 更像“一个长期在线、跨多个场景工作的私人 AI 助手系统”。它不只是会说话，而是有记忆、有工具、有权限边界，也能在多个渠道之间保持统一控制。

## 第二组：架构理解型

### 模拟 03

**面试官：** 你来讲讲它的整体架构。  
**你：** 我会从控制平面、执行平面和扩展平面三个角度来讲。控制平面是 Gateway，它是整个系统的中枢，负责接各个消息渠道、维护 session、做消息路由、管理插件运行时、提供 WebSocket 和 HTTP 服务，并且统一处理安全策略。执行平面是 Agent Runtime，它负责真正执行用户请求，包括构建系统提示、加载历史消息和记忆、调用模型、执行工具循环、处理流式输出和子 Agent 生命周期。扩展平面则是 Plugins、Context Engine、Memory、Browser、Canvas、Node capabilities 这些能力层。

如果按一条消息来讲，会更直观。消息先从某个通道插件进来，被标准化成统一结构；然后 Gateway 做去重、防抖、DM 配对检查和 routing 规则匹配，确定目标 Agent；再计算 sessionKey，把消息放进 per-session 队列；然后 Runtime 开始加载上下文，调用模型，如果模型要用工具，就进入工具循环；最后结果再通过对应通道发回去。也就是说，它不是“消息直连模型”，而是中间有一个完整的控制和编排层。

我觉得这个架构最有价值的一点是层次比较清晰。Gateway 负责管，Runtime 负责干，Plugins 负责扩。这样系统复杂度虽然高，但复杂度被放在了正确位置。

### 模拟 04

**面试官：** 为什么 OpenClaw 要采用 Gateway 中心化控制平面？  
**你：** 因为一旦系统接入多个通道、多个客户端和多个 Agent，就一定会出现大量共享状态，比如 session、routing、presence、health、token usage、channel runtime、plugin runtime。这些状态如果分散在各个客户端或各个通道内部，最终一定会漂。OpenClaw 用 Gateway 把这些共享状态统一收束起来，就能保证整个系统有一个一致的数据来源和控制入口。

另外一个原因是安全。它连接的不是抽象 API，而是真实消息渠道和高权限能力，比如 shell、browser、system.run、移动端设备控制。如果认证、配对、限流、权限控制分散在各处，就会很难保证一致性。集中到 Gateway 以后，整个入口和执行链路都更可控。

当然，中心化也有代价，比如 Gateway 会变成一个核心大模块，也会形成单点。但在这种多入口助手系统里，我觉得这是合理的取舍。因为它换来的是状态一致、运维清晰和安全边界统一。

### 模拟 05

**面试官：** 为什么同时要有 WebSocket 和 HTTP？  
**你：** 因为它们在 OpenClaw 里承担的是不同职责。WebSocket 更适合做实时双向控制协议，比如客户端连接 Gateway 之后要先 `connect` 握手，之后 Gateway 还要持续推送 `agent`、`presence`、`health`、`sessions.changed` 这种事件。这类实时双向通信很适合 WebSocket。

HTTP 则更适合 webhook、OpenAI 兼容接口、Control UI、Canvas 和健康检查这些服务型入口。比如 `/healthz`、`/readyz`、`/v1/chat/completions`、`/v1/responses` 这类路径，本身就是典型 HTTP 场景。外部系统往 Gateway 推 webhook 事件，也更自然走 HTTP。

所以这不是协议重复，而是把控制面和服务面分开了。WebSocket 管实时控制和事件流，HTTP 管接口兼容和托管服务。这样协议边界更清晰，也更方便系统演进。

## 第三组：消息、会话与路由型

### 模拟 06

**面试官：** 你说一条消息从进入系统到最后回复，大概经过哪些步骤？  
**你：** 我一般分成四段来回答。第一段是入站接入。消息先由 Telegram、WhatsApp、Discord 这些渠道插件接收，再统一标准化成内部消息结构。第二段是 Gateway 控制逻辑。这里会做去重、防抖、DM pairing 或 allowlist 检查、bindings 匹配、sessionKey 解析和队列入队。第三段是 Agent Runtime 执行。系统会加载 workspace、session transcript、memory、system prompt、tools，然后调用模型；如果模型返回工具调用，就执行工具并回填结果，再继续调用模型。第四段是出站发送。最终回复经过 streaming、分块和平台格式化后，再通过原通道发回去。

这里最关键的不是“步骤很多”，而是每一步都在解决不同问题。标准化解决多渠道接入差异，路由解决消息归属，sessionKey 解决上下文边界，队列保证同一会话的一致性，工具循环让模型具备执行能力，出站层则负责用户看到的真实体验。

### 模拟 07

**面试官：** `dmPolicy` 和 `dmScope` 有什么区别？  
**你：** 这两个很容易被混淆，但本质完全不同。`dmPolicy` 解决的是访问控制问题，也就是谁有资格发私聊给这个助手。比如默认 `pairing` 模式下，陌生人先拿配对码，不会直接触发 Agent；`allowlist` 是只有白名单用户能发；`open` 则是谁都可以发。

`dmScope` 解决的是上下文隔离问题。也就是消息进来之后，这些私聊应该被放进哪个会话里。比如 `main` 是所有 DM 共用一个主会话，`per-peer` 是按用户拆分，`per-channel-peer` 是按渠道加用户拆分，`per-account-channel-peer` 则是更细粒度地按账号、渠道、用户拆分。

所以一个管“能不能进来”，一个管“进来以后坐哪张桌子”。这点很关键，因为很多系统即使访问控制做得严，如果上下文没隔离，合法用户之间一样会串话，还是会有安全问题。

### 模拟 08

**面试官：** 为什么 `dmScope="main"` 在多用户场景下有风险？  
**你：** 因为 `main` 模式会把多个私聊来源聚合到同一个主会话里。在单用户自用场景下，这么做很方便，因为你可以在不同渠道延续同一段上下文；但一旦助手对多个真实用户开放，就会出现会话污染风险。

最典型的例子就是 Alice 和助手聊了敏感话题，Bob 再来问“我们刚才聊了什么”，如果两个人共用一个 session，模型完全有可能把 Alice 的上下文带给 Bob。这不是 prompt 层面的抽象风险，而是非常具体的 session isolation 风险。

所以 OpenClaw 文档里才会明确建议，多用户 DM 场景下要使用更安全的 `per-channel-peer` 或更细粒度模式。这个设计说明它把安全问题深入到了 sessionKey 层，而不是只停留在“入口做个 token 验证”。

### 模拟 09

**面试官：** 为什么要做 per-session 队列？  
**你：** 因为同一个 session 的上下文必须保持严格一致。如果一个会话里同时跑两个 Agent run，它们会同时读同一段历史、同时写工具结果、同时影响 compaction 和 usage 统计，最后上下文顺序就会乱掉。那样不仅模型回答不可预测，转录记录和后续会话也会被污染。

所以 OpenClaw 的设计是让同一个 session 在同一时刻只能有一个活跃 run，也就是 per-session 串行。这解决的是正确性问题，而不是性能优化问题。性能层面的控制，则交给全局并发池或不同 lane 去做。

换句话说，per-session queue 的本质是：同一个会话上下文，必须像数据库事务一样有顺序地推进，不能并发乱写。

## 第四组：Agent Runtime 与执行模型型

### 模拟 10

**面试官：** OpenClaw 的 Agent Runtime 和普通“调一次大模型”有什么本质区别？  
**你：** 最大区别是它不是一次请求，而是一个有状态的 Agent Loop。普通调模型更多是把 prompt 发给模型，拿回一段答案就结束了。OpenClaw 的 Runtime 则要处理一整个执行生命周期：先解析 session 和 agentId，再准备 workspace、skills、bootstrap 文件和 system prompt，然后开始模型调用。

关键在于中间的工具循环。如果模型决定调用工具，Runtime 需要执行工具、清洗工具结果、把结果回填上下文，再继续调用模型。这个过程可能发生多轮，直到模型输出最终文本。而且整个过程中还要处理流式输出、NO_REPLY、工具错误回退、compaction、retry 和 lifecycle 事件。

所以它更像一个“带状态的执行引擎”，而不是一个“问答函数”。我觉得这也是 OpenClaw 比很多演示型 Agent 框架成熟的地方。

### 模拟 11

**面试官：** `collect`、`followup`、`steer` 你怎么理解？  
**你：** 这三种模式其实都是在回答同一个问题：当前 run 还没结束时，如果用户又发了新消息，系统要怎么办。`followup` 最保守，就是等当前回合彻底结束，再把新消息作为下一轮输入。适合那种需要每轮闭合得很清楚的任务。

`collect` 更偏对话体验，它会把排队中的多条消息合并起来，等当前 run 结束后再作为一个 followup 输入，这样不会显得太碎。`steer` 更激进，它会在工具调用边界尝试检查排队消息，如果发现用户话题已经变了，就尽量停止后续无意义工具调用，把新消息导入当前执行流。

所以我的理解是：`followup` 强调稳定，`collect` 强调自然，`steer` 强调响应性。它们不是哪一个更高级，而是适合不同交互风格。

### 模拟 12

**面试官：** 系统提示为什么要动态组装，而不是写死？  
**你：** 因为 OpenClaw 的运行环境太动态了。不同 Agent 拥有不同工具、不同 skills、不同 workspace、不同 memory、不同安全边界，甚至是否启用沙箱、当前时间信息、reply tags 和心跳提示都会变化。如果写死一份超级 Prompt，会非常不精确，也会不断膨胀。

动态组装的好处是，可以按当前运行时只放必要信息。比如当前有哪些工具、当前工作目录是什么、有哪些 skills、当前应该注入哪些 bootstrap 文件、要不要带沙箱信息，这些都由运行时决定。这样 prompt 更精准，也更容易控制大小。

另外，从性能角度看，动态组装还能更好地维护 prompt cache 稳定前缀，因为它能把变化信息控制在必要范围内，而不是每次都重排一份庞大 prompt。

### 模拟 13

**面试官：** 子 Agent 为什么要用 `minimal` prompt mode？  
**你：** 因为子 Agent 通常是为一个局部任务服务，不需要继承主 Agent 的全部人格、记忆和背景。如果把主 Agent 的所有 system prompt、memory、skills、reply tags、heartbeats 都完整塞给子 Agent，会造成两个问题：一是 token 成本高，二是噪声很多，反而影响子任务聚焦。

`minimal` 模式的核心思想，是按任务边界裁剪上下文。保留子任务真正需要的工具和操作边界，比如 `AGENTS.md` 和 `TOOLS.md`，但不把所有长期上下文都强灌进去。这样子 Agent 会更轻、更快，也更不容易跑偏。

我觉得这个设计体现了一个很重要的观念：上下文不是越多越好，而是越贴近当前任务越好。

## 第五组：Memory、Context Engine 与插件型

### 模拟 14

**面试官：** 你怎么理解 OpenClaw 的 Memory 设计？  
**你：** 我觉得它最有意思的地方是，把记忆的主表达形式放回了文件。也就是说，真正长期保存的信息不是一个完全看不见的数据库，而是 `MEMORY.md` 和 `memory/*.md` 这类 Markdown 文件。这样用户能看到、能编辑、能校对，也更符合个人助手的透明性诉求。

数据库和向量索引当然也有，但它们更像加速层，而不是记忆本体。比如 `memory-lancedb` 会负责向量检索、自动召回和自动捕获，但它并没有取代文件型记忆，而是在增强文件记忆的可检索性。

所以如果一句话总结，我会说：OpenClaw 的记忆设计是“文件可见、索引增强、向量加速”，这比很多纯黑盒向量记忆更适合个人 AI 助手场景。

### 模拟 15

**面试官：** Pruning 和 Compaction 为什么要分开？  
**你：** 因为它们处理的是两个不同层次的问题。Pruning 更像每轮调用前的轻量整理，重点是削减大工具结果，减少上下文膨胀，但尽量不改主线消息结构。Compaction 则是当整个会话上下文真的快撑爆时，对旧历史做更重的压缩，比如生成摘要、保留最近消息、替换旧内容。

简单说，pruning 解决的是“这轮调用能不能更轻”，compaction 解决的是“这段长期会话还能不能继续活下去”。如果只有 pruning，长期会话最终还是会爆；如果只有 compaction，每轮调用成本又会过高。所以两者必须都存在。

### 模拟 16

**面试官：** Context Engine 为什么值得单独抽象？  
**你：** 因为“怎么构造上下文”本身就是一个高度变化、而且对效果影响巨大的能力。它不是简单把历史消息拼起来，而是要决定哪些内容该进上下文、什么时候做压缩、压缩策略是什么、是否要插入额外系统提示、子 Agent 上下文怎么控制等。

如果把这些逻辑写死在 Runtime 里，系统很快就只能有一种上下文策略。OpenClaw 把它抽象成 Context Engine，就可以在不破坏主执行引擎的前提下，支持更高级的检索、压缩和上下文维护方案。

所以我会把 Context Engine 理解成 Runtime 之外的一层“上下文策略引擎”，它让上下文管理也具备插件化和演进空间。

### 模拟 17

**面试官：** OpenClaw 的插件体系为什么比很多项目成熟？  
**你：** 因为它不只是把代码拆分成多个模块，而是真的建立了一个平台化扩展体系。它有 manifest、registry、loader、hooks、slots、Plugin SDK 和很严格的导入边界控制。插件不能直接深依赖核心 `src/**`，而要通过公共 SDK 接入，这就保证了核心和插件之间是契约关系，而不是源码耦合关系。

另外，它还很清楚地区分了哪些能力可以并行共存，哪些能力必须是唯一主实现。比如 memory 和 context engine 做成 slot，就是一个很成熟的做法。因为如果多个主实现同时接管同一职责，系统语义会很混乱。

所以我觉得它成熟，不是因为插件数量多，而是因为插件边界、生命周期和主实现冲突问题都被系统化考虑到了。

## 第六组：安全、工程化与总结型

### 模拟 18

**面试官：** OpenClaw 的安全模型有哪些值得说的点？  
**你：** 我觉得最值得说的是，它没有把安全简化成“加个 token”。因为它面对的是现实消息渠道和高权限工具，单一认证远远不够。它的安全模型是分层的，包括传输安全、Gateway 认证、设备身份、DM pairing、allowlist/open 策略、速率限制、Origin 检查、RBAC、工具权限和可选沙箱。

我尤其觉得它把 session 隔离也当成安全问题这点很成熟。很多系统只关心谁能进来，但没考虑进来以后是不是还处在正确的上下文边界里。OpenClaw 对 `dmScope` 的处理说明它把“上下文不会串话”也看作安全的一部分。

所以如果要总结，它的安全亮点不在于某一个特别炫的机制，而在于它把 AI assistant 真实会遇到的攻击面做了比较完整的建模。

### 模拟 19

**面试官：** 你觉得 OpenClaw 最值得学习的三个设计点是什么？  
**你：** 第一，我会选 Gateway 作为统一控制平面。因为它把多渠道、多客户端、多会话、多 Agent 和安全策略都收束到了一个中心，让系统有了统一数据源和统一控制入口。第二，我会选 Agent Runtime 的工程化执行模型。它不是简单调模型，而是把 session、队列、streaming、工具循环、容错和 subagent 组织成了一个长期运行框架。第三，我会选插件体系和上下文/记忆体系的边界设计。因为这决定了系统能不能持续演进，而不是写成一个大而全但不可维护的核心。

如果让我再补一句，我会说 OpenClaw 最值得学习的，不是它支持了多少功能，而是它把复杂性放到了正确边界里。

### 模拟 20

**面试官：** 如果让你借鉴 OpenClaw 的思路自己做一个类似系统，你会先做哪几块？  
**你：** 我不会一开始就追求功能多，而会优先搭四个骨架。第一是 Gateway，也就是统一控制平面，因为没有它，多入口系统状态会很乱。第二是 Session 和 Routing，因为上下文边界和消息归属必须先稳。第三是 Agent Runtime，也就是稳定的工具循环、队列和 streaming 机制。第四是权限模型，包括 per-agent tools 和高风险动作审批。

等这四块稳定了，我才会逐步做 Plugins、Memory、Context Engine 这些更高级的扩展能力。因为如果底层控制面和执行面都没搭稳，越往上加功能，系统越容易变成一个看起来很强、实际上很脆的 Demo。
