# HTTP Debug MCP Server 面试讲解提纲

## 一句话定位

这是一个面向外部 API 调试的 MCP Server，我用它来展示：当 MCP 工具要访问网络时，真正的设计重点是 allowlist、超时、响应裁剪和结构化返回。

## 适合怎么开场

可以先这样讲：

> 我做 `http-debug-mcp` 的目的，不是给模型无限制地发请求，而是用一个可运行的例子证明：外部 API 类 MCP 插件必须先解决网络边界问题，再谈能力暴露。

## 2 分钟讲解提纲

1. 先讲为什么做它
   真实业务里，很多 MCP 插件最后都会落到“调一个外部 API”。

2. 再讲能力设计
   - `http_get`
   - `http_post_json`
   - `inspect_response_headers`

3. 再讲核心限制
   - 必须通过 `--allow-hosts` 配置 host allowlist
   - 只允许 `http` / `https`
   - 所有请求都有超时
   - 响应只返回预览，不无限透传

4. 最后讲工程价值
   这个服务能让我把“如何做一个可控的网络型 MCP 工具”讲具体，而不是只停留在“我知道 MCP 能调 API”。

## 5 分钟展开讲法

### 1. 为什么单独做一个 HTTP 类插件

- 因为它是最接近真实业务的插件类型之一
- 很多企业内部 MCP 最终都是在封装 HTTP API
- 但它也是最容易被追问安全边界的一类能力

### 2. 这 3 个工具的分工

- `http_get`
  负责最常见的只读 HTTP 调试场景
- `http_post_json`
  演示发送结构化 JSON body 的能力
- `inspect_response_headers`
  用于只看响应头，默认优先尝试 `HEAD`，不支持时回退 `GET`

这样设计的好处是：既覆盖常见场景，又能体现我考虑过不同请求语义。

### 3. 为什么要做 host allowlist

- 如果不给 allowlist，模型就等于获得了任意网络访问能力
- 这会带来数据外发、SSRF、误调用未知服务等风险
- 所以我把外部访问先限制到明确的 host 列表

这里面试时可以强调：

> 我不是在做一个通用代理，而是在做一个受控工具。

### 4. 为什么要限制协议、超时和响应大小

#### 协议限制

- 只允许 `http` 和 `https`
- 直接拒绝其他协议

#### 超时限制

- 防止模型一次调用卡住
- 防止慢请求拖垮 Agent 整体体验

#### 响应裁剪

- 外部接口可能返回很大内容
- 如果把整个响应原样透传给模型，既浪费上下文，也不利于推理
- 所以我统一返回状态码、响应头和预览内容

### 5. 为什么返回结构化摘要，而不是原始响应

- 结构化摘要更适合模型理解
- 也更适合人类排查
- 我可以稳定地暴露状态码、headers、preview 这些关键字段

这本质上是在做“面向 LLM 的接口设计”，而不是传统意义上的 HTTP 透传。

## 高频追问与回答

### 1. 为什么不用一个通用代理工具，让模型传任意 URL？

因为那样风险太大。模型一旦获得无限制网络访问能力，就可能访问不该访问的服务，甚至把敏感数据带出去。对 MCP 工具来说，可控性优先于通用性。

### 2. 为什么 `inspect_response_headers` 要优先用 `HEAD`？

因为有些场景只关心 headers，比如缓存策略、内容类型、限流信息。这时用 `HEAD` 更轻量。如果目标服务不支持，再自动回退到 `GET`，这样兼顾了通用性和效率。

### 3. 为什么一定要做响应截断？

因为响应结果最终是给模型消费的。原样透传大响应，既占上下文窗口，也会稀释有效信息。截断后保留关键摘要，更符合 Agent 工具的实际使用场景。

### 4. 这个服务和 Postman / curl 有什么区别？

Postman 和 curl 是给人直接调试的，而 MCP HTTP 工具是给模型调用的。模型调用时，我更关注的是 allowlist、结构化返回、超时和输入约束，这些设计思路和传统调试工具不完全一样。

### 5. 为什么支持 `POST JSON`，但没有支持所有 HTTP 方法？

因为教学型插件的目标不是“全”，而是“有代表性”。`GET`、`POST JSON` 和只看 headers 的场景，已经足够覆盖大多数面试讨论点。如果后续需要，我再逐步扩展 `PUT`、`PATCH`、鉴权等能力。

### 6. 如果要继续增强，你会优先做什么？

我会优先补两类能力：一类是认证头或 token 管理；另一类是更细粒度的域名和路径级限制。这样会更贴近企业里的真实 API 插件。

## 面试时可以顺手补的一句话

> `http-debug-mcp` 说明我不只是知道“怎么调 HTTP”，而是知道“怎么把 HTTP 能力包装成一个可控、可被模型安全使用的 MCP 工具”。
