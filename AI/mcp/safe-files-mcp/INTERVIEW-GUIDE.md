# Safe Files MCP Server 面试讲解提纲

## 一句话定位

这是一个带安全边界的本地只读文件 MCP Server，我用它来展示：一个可用的 MCP 插件，重点不只是暴露能力，更是控制访问范围。

## 适合怎么开场

可以先这样讲：

> 在 MCP 场景里，文件能力是最常见也是最危险的一类能力。所以我专门写了一个 `safe-files-mcp`，只做白名单目录下的只读访问，重点演示路径校验、结果截断和风险控制。

## 2 分钟讲解提纲

1. 先讲为什么做它
   文件工具很实用，但如果没有边界，模型就可能越权读系统文件或者读超大文件。

2. 再讲我提供了什么能力
   - `list_files`
   - `read_text_file`
   - `search_in_files`

3. 再讲安全设计
   - 必须通过 `--root` 指定白名单根目录
   - 拒绝 `../` 目录穿越
   - 只读，不提供写能力
   - 限制单文件大小、搜索结果数量、目录条目数量

4. 最后讲价值
   这个服务不是为了把文件系统能力做全，而是为了证明我知道 Agent 工具开发里“能力边界”比“能力数量”更重要。

## 5 分钟展开讲法

### 1. 为什么文件类插件值得单独做

- 文件工具是很多 Agent 最先接入的一类能力
- 但它也最容易出安全问题
- 所以我把它拆成独立服务，方便面试时单独讲清楚安全思路

### 2. 这 3 个工具分别解决什么问题

- `list_files`
  解决“模型先看目录结构”的问题
- `read_text_file`
  解决“模型定位后读取内容”的问题
- `search_in_files`
  解决“模型先用关键词缩小范围”的问题

这 3 个工具组合起来，已经能覆盖大多数只读知识检索场景。

### 3. 我做了哪些核心安全控制

#### 白名单根目录

- 服务启动时必须传 `--root`
- 所有访问路径都只能在这个根目录之下
- 这样可以把风险边界从“整台机器”缩到“一个目录”

#### 路径越界校验

- 我会把相对路径解析成绝对路径
- 再检查解析结果是否仍位于根目录内
- 如果用户传 `../` 试图逃逸目录，直接拒绝

#### 只读设计

- 我没有提供写文件、删文件、改文件
- 因为面试展示阶段，先把最安全的能力做扎实，比一开始追求全功能更合理

#### 输出裁剪

- 限制单文件大小
- 限制搜索结果数
- 限制目录条目数
- 限制搜索深度

这几项限制的意义是：

> 不让一次工具调用把上下文窗口打爆，也避免模型拿到过量无用信息。

### 4. 为什么只支持文本文件

- 文件类工具最容易踩的坑之一就是误读二进制文件
- 所以我直接做了二进制内容检测
- 只把文本文件作为有效输入

这能同时解决两个问题：

- 避免乱码和无意义上下文
- 避免大文件或二进制文件带来的额外风险

## 高频追问与回答

### 1. 为什么一定要 `--root` 白名单？

因为文件系统权限天然太大。如果没有白名单，模型可能访问到 SSH key、系统配置、浏览器数据等敏感内容。`--root` 的作用就是把 MCP 的能力收敛到一个明确的、可审计的范围。

### 2. 为什么你只做只读，不做写入？

因为写入类工具风险更高，涉及误改、覆盖、删除和幂等性问题。面试场景下，我更想先展示“安全地暴露能力”的方法论，再逐步扩展到写入类工具。

### 3. 你是怎么防目录穿越的？

我把传入路径和根目录一起做绝对路径解析，然后判断最终结果是否仍在根目录内。如果不在，就说明发生了越界访问，直接拒绝。这比单纯判断字符串里有没有 `../` 更可靠。

### 4. 为什么还要限制文件大小和搜索结果数？

因为 Agent 工具不是传统后端 API。它的结果最终要喂给模型，过大的结果会造成两类问题：一类是浪费上下文窗口，另一类是让模型更难聚焦。所以我把结果控制也当成接口设计的一部分。

### 5. 这个服务和 IDE 自带搜索有什么区别？

IDE 搜索是给人用的，而 MCP 文件工具是给模型用的。给模型用时，除了“能搜到”，还要考虑返回结构、大小控制、路径权限和可解释性。所以设计重点不完全一样。

### 6. 如果要继续扩展，你下一步会加什么？

我会优先加两类功能：一类是按 glob 或后缀过滤得更细；另一类是支持返回更结构化的摘要结果。但我仍然会坚持只读和白名单这两个核心原则。

## 面试时可以顺手补的一句话

> `safe-files-mcp` 想证明的不是“我会读文件”，而是“我知道怎么把一个高风险能力收敛成可控能力”。
